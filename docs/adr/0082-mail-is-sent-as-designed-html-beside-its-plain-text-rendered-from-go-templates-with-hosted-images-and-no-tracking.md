# Mail is sent as designed HTML beside its plain text, rendered from Go templates, with hosted images and no tracking

Retires the part of [ADR 0033](./0033-mail-is-written-in-the-recipients-mail-locale.md) that rejected templates for mail, and the "plain text only for now" choice recorded beside the Resend sender since [ADR 0009](./0009-transactional-email-via-resend.md).
Everything else in ADR 0033 stands: mail is still written in the recipient's Mail Locale, in usted, from the per-sentence translated copy.

## Context

Every message this platform sends, all twenty-two kinds, is a plain-text body assembled with `fmt.Sprintf`.
That was a deliberate economy: no templating dependency, and none of the deliverability tuning HTML mail invites.
It was the right call while the mail was a handful of receipts.

It is no longer a handful.
A buyer now gets a Sale Confirmation, reminders to assign and to answer, Ticket Assignments, invoices, and a weekly Follow Digest, from a platform whose Storefront shows every Event with its Cover Image, its Thumbnail and its Organization's Logo.
The mail looks like none of that.
A plain-text message from an unfamiliar sender, about money, with long raw links, is exactly what people learn to distrust, and the Sale Confirmation does not even name the Organization the buyer paid.
The mails that must earn a click, the Digest and the reminders, compete with designed mail in the same inbox and lose.

A prototype of three visual directions, each rendered as the Sale Confirmation and the Follow Digest in both languages, was built, sent through Mailpit and judged in light mode, dark mode, Gmail-style forced inversion, 375px width and with images blocked.
The outcome is recorded on the throwaway branch `worktree-email-directions-prototype`, in `prototypes/email-directions/README.md`.

## Decision

**Every mail kind is sent multipart: a designed HTML part beside the plain-text part it already has.**
The plain text stays generated from the same message value and remains a complete message on its own, for every reader whose client shows it.
Staff and operator mail gets the HTML part too, because one consistent look is part of what makes the platform's mail recognisable as its own.

**The HTML is rendered in-process with Go's `html/template`.**
A small set of shared components (the page chrome, the Cover Image block, the Event row, the Organization row, the details box, the primary button, the footer) is composed per kind.
`html/template` is chosen for its contextual escaping: mail interpolates names, Event titles and Organization names that buyers and organizers typed, and an HTML body built by string concatenation would be one missed escape away from injecting markup into somebody's inbox.
Styles are written inline in the templates themselves, so no CSS inliner runs at build or send time.
The only `<style>` block carries what cannot be inline: the dark-mode overrides and the mobile breakpoint.

**One shared layout, the prototype's direction A, wraps every kind.**
A grey canvas, the Multiticketing mark and name above, one white rounded card at most 600px wide, and the footer below the card on the canvas.
The Organizer's identity lives inside the card, as the Organization's name in text and its Logo on a white tile, never as the chrome: there are no per-Organization colours, and the platform is the sender.

**Images are hosted, never embedded, and the mail never depends on them.**
Images are served from the public media bucket as email-safe renditions generated by the platform: a wide JPEG of the Cover Image, a square JPEG for the Thumbnail slot, a PNG of the Logo.
The originals are unsuitable, since they may be WebP, which desktop Outlook cannot show, and of any size.
Every mail reads completely with images blocked: no text is ever baked into an image, and a missing rendition omits the image rather than breaking the layout.
Embedding images as attachments was rejected because it makes every message heavier, Gmail sometimes lists them as attachments, and the Digest would carry a dozen.

**No open pixels and no click-tracking redirects, in any mail.**
Customers are in Ecuador, under the LOPDP; the Digest exists only by Marketing Consent; and links rewritten through a tracking domain are a known deliverability and trust cost, the opposite of the reason this change exists.
That a hosted image is fetched from our bucket is not tracking: nothing about the fetch is recorded or joined to a person.

**The Unsubscribe link stays on the Follow Digest alone** ([ADR 0034](./0034-marketing-consent-and-the-follow-digest-are-one-switch.md)).
Every footer instead says why this reader got this mail, who operates the platform, and where to ask for help.

**No switch.**
HTML mail ships for every kind when it merges.
The plain-text part is unchanged in substance, so a rollback is a revert, and a switch would be a second rendering path to keep tested forever.
The check that stands in for a switch is a real send of every kind to Gmail, Apple Mail and Outlook inboxes, in light and dark mode, before merge.

## Considered options

- **Stay plain text and only improve the copy.**
  Zero deliverability risk and no new machinery.
  Rejected because the problem is recognisability and trust, which words alone cannot fix next to designed mail, and because the Digest's whole job is to make Events look worth a click.
- **MJML compiled at build time.**
  Excellent client compatibility out of the box.
  Rejected because it puts a Node toolchain into the Go build and produces markup we would then template anyway; the prototype showed that hand-written table layout reaches the same compatibility (86-93% supported in Mailpit's check, the same for every direction).
- **React Email rendering Go templates in a build step.**
  Familiar to the frontend half of the repo.
  Rejected for the same toolchain reason, and because it splits each message's copy, which lives in Go, from its markup.
- **`text/template` with manual escaping**, the option ADR 0033 rejected as machinery.
  Rejected again, now for a different reason: for HTML the escaping is the point.
- **Per-Organization branding (colour, sender name).**
  Rejected: no brand colour exists in the data model, per-Organization colours need contrast checks the platform cannot make for them, and the sender is the platform.
- **A per-identity switch for HTML.**
  Rejected for the reason given under "No switch".

## Consequences

**Every message value gains an HTML rendering, and every provider sends it.**
The SES and Resend senders send both parts and the attachments together.
Dev gains Mailpit as its mail sink, so the HTML can be seen as a reader sees it.

**The Cover Image, Thumbnail and Logo each gain a stored rendition, produced when the original is set and filled once for everything that already exists.**
An image the platform could not render is simply absent from mail until a later run produces it.

**Gmail ignores `prefers-color-scheme` and force-inverts.**
Dark mode is therefore a progressive enhancement for Apple Mail and Outlook.com, and every colour must also survive Gmail's inversion.
The Logo tile stays white only because it is painted with a `background-image` gradient as well as a background colour; a "simplification" that drops the gradient breaks dark mode in Gmail without breaking any test that does not render in Gmail.

**The primary blue fails WCAG AA on the grey canvas at small sizes** (4.15:1).
It is used only on white, for the button and for links inside the card; links on the canvas, which is the footer, use the body text colour, underlined.

**Desktop Outlook gets a degraded but readable mail**: square corners, no dark mode, no responsive breakpoint.
This is accepted, not a defect.

**The golden HTML of every kind in both languages becomes part of the test suite**, so a change to a shared component shows up as a diff across every mail that uses it.
