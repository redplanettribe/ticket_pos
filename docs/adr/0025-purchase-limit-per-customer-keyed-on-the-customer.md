# The Purchase Limit is keyed on the Customer, checked at begin-checkout, and is a deterrent rather than a defence

To stop one person taking a Free Ticket Type's whole allocation we chose a **Purchase Limit**: an optional positive integer on the Ticket Type, NULL meaning unrestricted, counted against the **Customer** — the platform-global email identity of ADR 0010 — as their active Ticket Sales plus their live Capacity Holds (ADR 0013). We rejected keying it on the Tax ID each Ticket Sale snapshots, because the validation gradient of ADR 0016 is deliberately uneven: `cedula` and `ruc` are checksummed but `passport` is accepted on shape alone, so selecting `passport` and typing a fresh string is a *cheaper* bypass than cycling email addresses, and because CONTEXT.md states the same Tax ID may appear on several Customers, so a Tax ID key would falsely refuse a shared company RUC. We rejected requiring a Customer Session to buy a rationed Ticket Type, which would put a sign-in wall in front of exactly the frictionless free tickets the limit exists to protect while only costing an evader one passcode per throwaway inbox. We rejected inferring the limit from a zero price, because a free RSVP for a large venue is a legitimate unrestricted case.

## Consequences

- **It is a deterrent, not a guarantee.** A Customer is identified by a self-declared, unverified email at guest checkout, so anyone willing to type a second address defeats the limit. This stops the buyer who takes too many because nothing stopped them; it does not stop a determined evader. Do not read the Purchase Limit as an invariant, and do not "harden" it by forcing sign-in without revisiting this ADR.
- **The allowance moves exactly like capacity.** Active Ticket Sales and live Capacity Holds both consume it, so a Sale Reversal returns it and a failed or expired Payment releases it. The hold arm is what stops a buyer with several payment pages open settling more than once, and it reuses the existing hold window rather than introducing a second duration. A free checkout is born approved (ADR 0017) and so never creates a hold; the hold arm matters only for a *paid* rationed Ticket Type.
- **It is checked at begin-checkout and deliberately NOT re-checked under lock at commit.** Capacity is checked there because overselling a venue is a real physical failure; a Purchase Limit exceeded by one in a pathological interleaving is harmless. Enforcing it at commit would open a new route into the `PAYMENT_APPROVED_WITHOUT_SALE` incident — the platform holding a buyer's money for a ticket it refused, resolved by hand by a Platform Operator. The accepted worst case is one Customer holding limit+1. The asymmetry with capacity is intentional.
- **Lowering a limit is never retroactive.** It governs future checkouts only, like Fee Handling. A Customer holding three when the limit drops to one keeps all three, so `held > limit` is a legitimate state: remaining is `max(0, limit - held)` and must never be asserted non-negative. Nothing is reversed, flagged, or alerted on.
- **A Sale Import refuses rows that would breach it**, accumulating a running per-(Customer, Ticket Type) tally across the file so rows in one batch count against each other — without that, a single upload of identical rows would defeat the limit and make the refusal decorative. Only offending rows are rejected, matching how the preview reports every other row problem. An Organization importing history recorded before they set a limit must raise or clear it, import, then set it back.
- **In-person sales are unaffected, for now.** `in_person` is a recognised Sales Channel in list filters, Tax ID rules and reversal rules, but no endpoint records an In-Person Sale yet. When that POS lands, a Purchase Limit should be surfaced to the staff member as a warning they may proceed past — they are looking at the person — and the sale should consume the allowance.
- **The refusal is its own error code, `PURCHASE_LIMIT_EXCEEDED`**, distinct from `CAPACITY_EXCEEDED` so a Customer is never told the Event is full when it is only their own allowance that is spent. Storefront copy is keyed on the code per ADR 0023.
- **A signed-in Customer's remaining allowance is readable; nobody else's is.** The public Event read reports holdings only for the Customer Session that carried the request. No unauthenticated per-email lookup is added: it would be an oracle revealing whether a given address had bought a given Ticket Type.
- **Griefing needs no countermeasure.** A guest can consume another person's allowance by typing their address, but the Sale Confirmation and its working Confirmation Link are emailed to that address — the griefer spends effort giving the victim a ticket, and on a paid Ticket Type pays for it too.
- **The column is additive and nullable with no backfill**, so every existing Ticket Type keeps unrestricted behaviour and no Ticket Type becomes harder to buy as a result of shipping this. NULL rather than a sentinel: "not rationed" and "allows N" are different statements, and only NULL says the first without inviting arithmetic on it.
